# 需求澄清与领域语言

需求有歧义、关键取舍未定，或任务需要先方案后实施时使用；通用约束见 [core](core.md)。

- 先查已有需求、契约和代码，仓库里能查到的不问用户。
- 一次只问一个问题，等用户答完再问下一个；每个问题都给出推荐答案和理由。
- 先问答错会返工的问题：行为、权限、兼容性、数据与验收；不影响实现的细节不问，已确认的决定不重复问。
- 用户说“待定”的问题记下来，接着问下一个；写方案时原样列进待确认，不替用户补上答案。
- 关键问题已明确或由用户标为待定后，主动总结已确认内容与未决问题，进入方案，不要求用户说出结束澄清或开始写方案的指令。
  没有需要澄清的问题时，说明依据后直接进入方案；用户明确希望继续讨论时按其节奏推进。
- 不要求用户预先填写完整验收标准，由 Agent 结合仓库和对话整理，并就影响业务含义的歧义向用户确认。
- 澄清答案和对方案细节的认可不等于实施授权，先方案后实施的任务仍须在方案交付后等待用户明确同意实施。
- 沿用项目领域术语，用反例澄清同名异义；当前实现不能代替预期行为。
  术语与契约冲突时明确展示，确认后更新原有真源。
- 需要长期保留的术语和重要取舍写入项目已有文档；结论写回已有需求或方案，保留验收与剩余问题。
