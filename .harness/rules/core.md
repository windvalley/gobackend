# 基础研发规范

项目启用 harness 时遵循本规范，分析、设计与评审类任务同样适用，开始任何任务前先读完本文。
门禁的具体命令与项目事实见 `harness.md`，配置以项目内的 `.harness/*.json` 为准。

## 任务分级

开始前先识别用户当前请求的意图，再判断任务属于哪一级，在第一条回复里说明判断和依据。
任务分级依据需求范围和影响，不取决于固定话术。

同时满足以下条件的任务直接实施：

- 用户当前要求的是小优化、小迭代或缺陷修复，且需求已明确；仅要求分析、评估或讨论时保持只读。
- 不改库表结构与迁移，不改对外接口契约、权限与数据兼容性。
- 预计代码改动少于 `.harness/config.json` 里 `intent.plan.maxLines` 规定的行数，未配置时按 500 行；测试、文档与锁文件不计。

不满足任一条件，或者拿不准时，先方案后实施：

1. 探索：先读仓库，回答需求涉及的能力现在有没有、做到了哪一步，相关的数据结构、接口与校验规则定义在哪，有没有看起来做了但没闭环的地方。
   每条结论附 `文件:行号`，找不到就说找不到，不推测；这一步不提问，也不写代码。
2. 澄清：按[需求澄清](method-requirements.md)逐个询问影响行为、权限、兼容性和验收的关键问题。
   关键问题已明确或由用户标为待定后，主动整理理解并进入方案，保留未决问题，不要求用户宣布问题问完或指挥写方案。
3. 方案：按[设计与任务拆分](method-design-planning.md)写验收清单、行为说明与实施方案。
4. 停下等授权：交出方案后停止。
   最初提出需求不能替代对已交付方案的实施授权，不根据某个固定词语认定授权。
   用户表达开始实施的意思之前（“开始实施”“按方案做”“可以，动手吧”等），不写测试，也不改生产代码；只回答某个澄清问题的“好”“可以”不算。
5. 授权后连续执行到完成：用户表达开始实施的意思就是授权，不需要用户再执行任何命令。
   项目启用了 `plan-first` 预设时，先按 `harness.md` 照录用户原话记录授权，然后按实施方案的顺序推进，不必每一步等用户安排，直到验收全部通过、交付证据齐全。
   遇到缺权限、需要业务拍板、改动范围明显超出方案、同一个问题连续三轮没有解决时，停下来说明情况。

直接实施的任务在实施中发现越过了上面的条件，停下来补方案，等用户同意后再继续。
直接实施的任务也建议写验收清单，独立评审据此核对需求符合度。
用户在当前对话里明确要求了不同的节奏时，按用户的要求做。

## 协作分工

- Agent 根据仓库事实理解需求，主动补齐验收标准，涉及业务含义的歧义与用户确认，并把已授权的实施工作推进到完成。
- Agent 按项目规则准备任务分支和工作环境，必要时自行创建或复用符合隔离要求的 Worktree，不要求用户预先手工准备。
  保留用户已有改动，不占用其他任务的工作区。
- 实现、提交、验证、独立评审和已获授权的交付由 Agent 连续执行，不把命令清单交给用户逐条运行。
  本地交付的合并在本机完成；远程交付的远程提交指推送任务分支与创建或更新 PR/MR，合并由团队在平台上完成。
  分析、评审和诊断类请求保持只读，不因此取得实施、合并或推送授权。
- 需要用户决定或必须由人亲自执行时，说明原因、具体对象和操作方式；用户完成后接续剩余工作。
- 交付时给出结果入口、逐条验收证据、验证与评审结论、最终合并状态和待处理项，区分配置就位、已验证和未验证。

## 验收与范围

- 修改生产代码前检查已有实现、测试、接口和配置，确认复用、扩展还是新建。
- 明确可验证的目标、非目标、正常路径、边界条件、失败与恢复路径、安全约束。
- 行为、权限、兼容性或失败语义的未决问题须经用户确认，不按当前实现推断产品语义。
- 需求有歧义时先确认影响验收的那几条，不追问不影响实现的细节。

## 测试先行

实现功能、修复缺陷或改变可观察行为时默认先红后绿，直接实施的任务同样适用；配置和脚本按是否改变行为判断。
纯文档、分析、规划、评审和复盘不要求先写测试；行为不变的重构从已有测试通过的状态开始，完成后验证受影响行为。

1. 红灯：把每条验收标准写成测试，标明是单元、集成还是 E2E；逐个运行，确认它们因为行为尚未实现而失败，记下命令与失败输出。
2. 绿灯：有效失败之后才写最小实现，每改一步就跑目标测试，失败就读报错修复，直到全部通过，再跑受影响的回归。
3. 重构：只在目标测试与回归都通过时重构，每次重构后重跑对应验证。

- 未发现测试、夹具损坏、依赖缺失、断言写错都不是有效的失败，先修测试环境。
- 禁止删除测试、弱化断言、跳过测试或检查、用 only 限定、mock 被测实现，或先写实现再倒推测试。
- 确实无法先写测试的改动（例如纯样式调整、外部平台限制），说明原因并给出替代验证，不宣称已经测试先行。

## 测试范围与成本

- 按影响范围选测试，默认不跑全量。
  按验收、最终 diff、调用方和共享依赖决定范围。
- 扩大到全量须说明依据：影响面广、无法界定范围、跨模块回归或用户与 CI 要求。
- 代码、测试、依赖和环境未变化时复用已通过的结果，不重复执行。
- 记录选测依据、命令和结果；未执行的项说明影响与补验方式，不宣称全量通过。

## 安全编码

- SQL、命令、模板和表达式禁止拼接外部输入，必须参数化或走白名单；ORM 的 raw 接口同样适用。
- 路径拼接须归一化并做白名单校验，不能只过滤 `..`。
- 请求与跳转目标须校验协议与域名，禁止直接使用用户输入。
- 解析外部数据时禁用外部实体；不可信数据不得直接反序列化为对象。
- HTML、JS 与属性中的用户输入按上下文转义，不以全局过滤替代。
- 口令、密钥和令牌禁止硬编码，用环境变量或配置注入；发现既有泄露须上报。
- 新增依赖固定版本，禁止来源不明的安装脚本；不向未审批的端点发送源码、日志或凭据。

## 完成证据

- 从约定的真实入口验证用户可见结果与失败恢复，区分已验证、未验证和外部阻塞。
- 夹具与 fake 只证明受控契约；真实服务、系统能力或第三方协议要按风险实测。
- 交付前自审，按验收清单逐条给出结果与证据（命令、输出或截图位置）；有实施方案时，在里面标出每一步的完成情况与验证方式。
- 报告已执行的测试、回归和人工验证；未运行的标 `not_evaluated` 并说明原因、影响和下一步。
- 只有必需验证全部通过、没有未说明的失败或阻塞时，才可以声称完成。
