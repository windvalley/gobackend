# 设计与任务拆分

任务需要先方案后实施时使用，分级见 [core](core.md)。

方案由三份文件组成，放在任务分支里一起提交：

| 文件 | 内容 |
| --- | --- |
| `.harness/acceptance/<分支名>.md` | 验收清单：应该发生什么、绝对不能发生什么、失败时怎么办，每条都能判定对错；独立评审按它逐条核对 |
| `docs/changes/<change-id>/spec.md` | 行为说明：用户卡在哪、目标行为、失败时怎么办、这次不做什么、待确认 |
| `docs/changes/<change-id>/plan.md` | 实施方案：验收到测试的对应、实现顺序、交付前的检查、环境与依赖、复用的已有能力 |

- 分支名里字母、数字、`.`、`_`、`-` 以外的字符换成 `-`；已有对应文档直接复用。
- 项目约定了别的方案目录时沿用，并同时修改 `.harness/config.json` 的 `intent.plan.markers` 与 `plan-before-code` 规则的放行路径。
- 交出方案后停下等用户表态；用户表达开始实施的意思后，连续执行到完成。
  项目启用了 `plan-first` 预设时，先照录用户原话记录授权，见 `harness.md`。
- 用[验收清单](../templates/acceptance.md)、[行为说明](../templates/spec.md)与[实施方案](../templates/plan.md)模板，删掉不适用的章节。
- 实施方案的第一步把每条验收标准对应到测试，标明单元、集成还是 E2E；后面的步骤写清实现顺序、每步的验证方式和什么时候算完成。
- 按方案连续执行时，每完成一步在实施方案里标出完成和验证方式。
- 以调用者负担和已有架构约束判断接口；不为想象中的扩展引入抽象，不把设计建议变成未经授权的重构。
- 按可验收行为纵向拆分，注明验收、真实阻塞关系和验证入口。
- 跨模块迁移按兼容新增、分批迁移、删除旧实现推进；每批保持必要验证通过，共同集成前不宣称整体可交付。
- 本方法不自动授权多 Agent 委派。已授权并行时明确责任与隔离边界，合并后仍须验证整体行为。
